# TPC-DS on KORE vs DuckDB (second benchmark family)

Everything here is generated by `gen_data.py` (DuckDB `dsdgen`, the official generator code, default seed) and
`run_ds.py` (DuckDB reference run, one KORE process per query, answer comparison, classifier). Results live in
`results/` (git-ignored); data in `data/` (git-ignored).

    python gen_data.py --sf 0.1 --out data/sf0.1 ; python gen_data.py --sf 1 --out data/sf1
    python run_ds.py duckdb --data data/sf1 --sf 1 ; python run_ds.py kore --data data/sf1 --sf 1 --repeats 2 --timeout 300
    python run_ds.py report --sf 1

## Method and honest caveats

* **Reference engine is DuckDB 1.5.6, not an official answer set**: `tpcds_answers()` raises "Don't have TPC-DS answers
  for SF 10" in this build, so no independent oracle exists. A "match" means KORE agrees with DuckDB.
* The 99 queries are the ones `tpcds_queries()` ships (DuckDB's Spark-flavoured TPC-DS text, default substitution
  parameters). **No dialect rewrites were needed or applied** (`REWRITES` in `run_ds.py` is empty); both engines run identical text.
* Data: KORE reads CSV (dates stay ISO strings, DECIMAL is a double, types sampled from 2000 rows by the loader). DuckDB
  reads Parquet with native DATE / DECIMAL types. Text columns are declared with a `name::str` header suffix in the CSV
  (a small loader feature added for this work, `kore-ffi/src/lib.rs`): without it the sampled inference read all-digit
  text such as `ca_zip` as BIGINT (and would silently drop leading zeros).
* Comparison: positional (KORE is asked for `SELECT * FROM (<q>) AS t(c0,..)`, because result sets have duplicate and
  unnamed columns), order-insensitive multiset with 1e-6 relative float tolerance, strings stripped, midnight timestamps equal
  dates, **NULL equals the empty string** (KORE's CSV loader reads an empty field and a quoted empty string both as NULL;
  only `c_login` is affected). ORDER BY..LIMIT queries that differ only in tie choice would be classed `OK_TIES`
  (none occurred). Timings: warm-up plus best of 2 (sf0.1) / 3 (sf1) runs, on a shared machine (noise caveat below).
* **Weak spots of the check**: 18 of 99 queries return 0 rows at sf0.1 (the stock parameters are tuned for larger data), so
  sf0.1 "OK" for those proves little; at sf1 only Q17 returns 0 rows. Row counts are in the table.

## Results

| | sf0.1 | sf1 |
|---|---|---|
| **Before fixes** (first complete run, harness bugs fixed) | OK 82, WRONG 8, ERROR 6, TIMEOUT 3 | not run on the unfixed build |
| **After fixes** | **OK 99, WRONG 0, ERROR 0, TIMEOUT 0** | **OK 97, WRONG 0, ERROR 0, TIMEOUT 2** (Q47, Q95: more than 300 s per query budget) |
| Geometric mean over agreeing queries, KORE vs DuckDB | 26.4 ms vs 13.2 ms (99 queries) | 125.4 ms vs 44.2 ms (97 queries) |
| Queries where KORE is faster | 37 of 99 | 32 of 97 |

The sf0.1 "before" column is the first full run **after** I fixed my own harness mistakes (Decimal normalisation, CTE
wrapper) but before any engine change and with the loader type issue still present, so some of its 8 WRONG are
loader typing (zip codes read as numbers: Q15, Q45, Q50, Q81; empty-string/NULL: Q30) rather than engine bugs; the engine
bugs among them are Q27, Q36 (constant column type) and Q62 (dropped column, see below). The ERROR queries were Q6, Q40, Q49, Q80,
Q93, Q99; the TIMEOUTs Q35, Q69, Q72. Overall KORE is about **2.8x slower than DuckDB (geometric mean) at sf1** and about
2x at sf0.1: this does NOT generalise the TPC-H parity result. Where it loses badly at sf1: Q70 (13.6 s vs 34 ms, ROLLUP + window), Q22 (7.2 s vs 0.2 s,
ROLLUP), Q57 / Q47 (window self-joins), Q5 (4.8 s vs 57 ms, UNION ALL of CTEs), Q4 / Q11 (CTE self-joins).
Timing noise: the machine was shared with other agents' builds and tests; DuckDB alone varies 1.5x between runs and the
sf1 KORE run overlapped with a leftover test process, so per-query ratios below 2x are not meaningful.

## Silent wrong answers and bugs fixed (regressions in `kore-sql/tests/ds_regress.rs`)

| Bug | Minimal repro | Fix |
|---|---|---|
| `SELECT expr, *` / `SELECT *, expr` silently dropped the expression (Q62, Q99: column came back NULL / missing) | `select id*10 as x, * from t` | `project()` only short-circuits when every item is `*` |
| A constant (or other non-aggregate) select item next to GROUP BY became TEXT, floats rounded to 4 digits (Q27, Q36) | `select 0 as g, k, sum(v) from t group by k` | typed column via `vals_to_column`; same fix for GROUP BY on a select alias of a computed expression |
| Comma join after an explicit join was a parse error (Q40, Q49, Q80, Q93) | `from a left join b on .. , c where ..` | comma tables parsed after explicit joins are moved in front of INNER/LEFT/CROSS joins (RIGHT/FULL/SEMI/ANTI: still an error) |
| ORDER BY a qualified GROUP BY column that the select list renames, together with `HAVING count(*)` (Q6) | `select a.g gg, count(*) from t a group by a.g having count(*)>=1 order by a.g` | `lift_aggregates` maps the ORDER BY item to the select alias |
| `EXISTS (select .. from t1, t2 ..)` / NOT EXISTS over a multi-table subquery ran per outer row (Q35, Q69 timed out, Q10 took 13 s) | see Q35 | subquery minus its one correlated equality is run once and becomes an IN list (NULL outer key: EXISTS false, NOT EXISTS true) |
| Explicit `JOIN .. ON` chains ran left-deep in written order, and a trailing LEFT JOIN disabled comma-join planning (Q72 timeout, Q49/Q80 slow) | `from a join b on .. join c on .. left join d on ..` | leading INNER joins become planner joins; planner stays on with trailing LEFT JOINs |
| Loader: all-digit text columns inferred as BIGINT (leading zeros lost) | `ca_zip` | `name::str` header hint |

New switches in `kore-sql/src/testing.rs`: `no_exists_multi`, `no_inner_implicit`, `no_planned_tail` (env `KORE_NO_EXISTS_MULTI`, `KORE_NO_INNER_IMPLICIT`, `KORE_NO_PLANNED_TAIL`).
Known unfixed hazard found on the way: a reference to a column that does not exist evaluates to NULL instead of an error
(`select nosuch + 1 from t` returns NULLs). That is how the `SELECT expr, *` bug produced silent garbage; a binder pass that
rejects unknown columns is the right fix and was not attempted.

## Remaining failures, ranked

1. **Q47** (sf1, about 66 s per run, budget exceeded): `v1 JOIN v1 lag JOIN v1 lead` with `rn = rn + 1` / `rn = rn - 1`; the offset
   equality cannot be a hash key, so the join builds 10.8M wide rows (12 string columns) on the four text keys and filters afterwards.
   Needs an expression-key join (key `rn - 1`). The window phase of `v1` also costs 2.7 s for 65k rows.
2. **Q95** (sf1, over 300 s): `web_sales` self-join CTE `ws_wh` used in two IN subqueries; not profiled.
3. Slow but correct at sf1 (more than 20x DuckDB): Q70, Q22 (ROLLUP paths), Q5, Q57, Q4, Q11, Q75, Q6, Q39, Q77.
No query currently returns an error or a different answer.
